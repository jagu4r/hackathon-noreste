1 · Orwel internals

Qué pasa realmente bajo el capó

Orwel parece "una línea para trackear", pero detrás hay un pipeline pensado para no perder datos ni degradar la app del cliente. Conocerlo te ayuda a construir mejor sobre él.

El flujo de ingesta, de extremo a extremo

Los eventos se encolan localmente y se envían por lotes; si el batch falla, hay reintento individual y flush al cerrar la página.

  • Resolución de visitante. ID estable derivado del fingerprint (UUID v5 determinista), persistido en localStorage. Reconoce al visitante entre sesiones sin login.
  • Cola resiliente. Eventos en localStorage (máx ~1000). Batch a /ingest/batch (máx 100); fallback individual; auto-flush en beforeunload.
  • Pipeline de lead. conversion → traits → enriquecimiento de empresa (Lusha) → upsert con dedup → integraciones (webhook/Brevo) → resumen IA → notificación.

Personalidades (orwel-mind): estadística, no IA

Orwel infiere 12 rasgos de cada visitante con el Teorema de Bayes, no con un LLM. Cada evento es evidencia que actualiza la probabilidad de cada rasgo — como un detective. Pruébalo:

Simulador · personalidad bayesiana

Pulsa acciones del visitante y observa cómo se actualizan los rasgos en vivo. Determinista, gratis, explicable.

Por qué Bayes y no un LLM aquí

Determinista (mismo input → mismo output), explicable (puedes auditar cada actualización), instantáneo y gratis. Un LLM sería caro, lento, no reproducible y podría alucinar un rasgo. Es el caso de libro de "no todo es IA".

2 · Multi-tenancy a escala

RLS seguro… y rápido

El aislamiento por tenant es fácil de implementar inseguro o lento. Estos son los detalles que solo importan cuando creces.

RLS con el claim en el JWT

policy + índice compuesto
alter table items enable row level security;

create policy "items: solo mi workspace" on items
  for all using (workspace_id = (auth.jwt() ->> 'workspace_id')::uuid);

-- El filtro de tenant va PRIMERO en el índice compuesto.
create index on items (workspace_id, created_at desc);

El error #1 a escala: N+1 queries

Listar 50 candidatos y, por cada uno, pedir su vacante = 51 consultas. A pocos datos no se nota; con tráfico real, tu base muere.

✗ N+1 (51 viajes a la BD)

const cs = await getCandidatos()
for (const c of cs) {
  c.vacante =
    await getVacante(c.vacante_id) // ✗
}
~510 ms

✓ Un join / select anidado

const cs = await supabase
  .from('candidatos')
  .select('*, vacante:vacantes(*)')
  // 1 sola consulta ✓
~12 ms

Cómo detectarlo

Si ves un await dentro de un for/map que pega a la base o a una API, es casi seguro un N+1. Resuélvelo con un join, un in (...), o DataLoader para agrupar.

  • Agrega en SQL, no en JS. No traigas 100k filas para sumarlas en memoria: count(), sum(), group by en la base. Ahorras memoria y red.
  • Connection pooling. Serverless abre una conexión por invocación → agotas Postgres. Usa un pooler (PgBouncer / Supabase pooler) en modo transacción.
  • Paginación con cursor, no offset. OFFSET 100000 hace que la base recorra 100k filas. Pagina por created_at < ? (keyset).
  • Streaming + caché en proceso. Pinta skeletons al instante; un cache con TTL evita que N peticiones idénticas choquen contra un statement timeout (ver skill svelte-loading).

La intuición

El ahorro no viene de un truco, sino de tres decisiones combinadas: no mandes texto crudo (extrae), no uses el modelo caro para todo (rutea), y no recalcules lo que no cambió (cachea). El mismo resultado, una fracción del costo.

Matriz de ruteo: qué modelo para qué tarea

TareaModeloPor qué
Extraer campos, clasificar, formatear, traducirPequeño / baratoMecánico y verificable. Un modelo chico acierta y cuesta ~20×menos.
Razonar, sintetizar, decidir, redactar finoGrande / potenteSolo donde la calidad del juicio mueve el resultado.

4 · Resiliencia

Las APIs fallan. Tu producto no debería.

Proveedores de IA y bases de datos fallan de forma transitoria (rate limits, timeouts, 503). Un producto serio lo absorbe sin que el usuario se entere.

Visualizador · reintentos con backoff exponencial

Simula una llamada inestable. Mira cómo el reintento con espera creciente la rescata, en vez de tirar un error a la primera.

backoff exponencial + degradación
async function withRetry(fn, retries = 2, base = 300) {
  for (let i = 0; i <= retries; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === retries) throw e;        // se acabaron los intentos
      await sleep(base * 2 ** i);          // 300ms, 600ms, 1200ms…
    }
  }
}
  • Backoff exponencial + jitter. Si todos reintentan al mismo tiempo, vuelves a tumbar al proveedor (thundering herd). Suma un margen aleatorio.
  • Idempotencia. Si reintentas un POST que crea algo, podrías duplicar. Manda una Idempotency-Key y dedup en el servidor (Orwel deduplica conversiones por clave compuesta justo por esto).
  • Circuit breaker. Si un servicio lleva N fallos seguidos, deja de llamarlo un rato (falla rápido) en vez de acumular timeouts que ahogan tu app.
  • Degradación elegante. ¿Falló el scoring de 3 de 200 candidatos? Devuelve los 197 marcando los 3. Un 98% útil supera a un error total.
  • Timeouts en todo. Una llamada sin timeout puede colgar un worker indefinidamente. Pon un tope y trátalo como fallo.

5 · Calidad medible

Si no lo mides, no sabes si tu IA mejora o empeora

"Se ve bien" no es una métrica. Tratar la IA como software serio significa observarla y evaluarla con datos.

Observabilidad

  • Loguea cada llamada: prompt, modelo, tokens (in/out), latencia, costo y resultado. Sin esto, depurar IA es a ciegas y la factura es una sorpresa.
  • Traza el flujo completo (request_id) cuando una operación encadena varias llamadas (extraer → puntuar → resumir).

Evals: tu red de seguridad ante cambios

Un cambio "pequeño" de prompt o de modelo puede romper tu feature en silencio. Un dataset dorado (entradas + salida esperada) te avisa.

  1. Reúne 20–50 casos reales con su respuesta correcta. Versiónalos en el repo (evals/dataset.jsonl).
  2. Corre el modelo contra el dataset al cambiar prompt/modelo (no en cada commit: cuesta).
  3. Mide: % correcto, % de formato válido (JSON parseable), costo y latencia por caso.
  4. Compara versiones. ¿El prompt nuevo subió el acierto del 82% al 91% sin subir el costo? Adelante. ¿Lo bajó? Revierte.

Guardrails

  • Valida el esquema de toda salida estructurada antes de actuar. Si no cumple, reintenta o degrada — nunca ejecutes sobre JSON inválido.
  • Inyección de prompt: separa instrucciones de datos del usuario con delimitadores; nunca dejes que contenido externo redefina el system prompt.
  • Aterriza la respuesta (grounding): en RAG, exige citar las fuentes recuperadas y permitir "no sé" en vez de inventar.

Para el hackathon

No montes evals completos en un fin de semana — pero ten 5 casos a mano y córrelos antes de la demo. Si tu IA falla justo frente al jurado, esos 5 minutos de prueba te habrían salvado.

6 · Spec-Driven Development

Cómo lograr que la IA no alucine (y dé resultados replicables)

En palabras simples

Antes de que la IA escriba código, escribes una breve especificación: qué cambia y por qué. La IA —y tú— trabajan contra ese contrato. Es el plano antes de construir: evita que el modelo improvise.

Pedirle a un asistente "hazme la feature X" sin contexto es la receta para que invente archivos y dé un resultado distinto cada vez. El desarrollo guiado por especificaciones lo soluciona; la herramienta de referencia es OpenSpec, y TeamUp la usa.

✗ "Vibe coding" sin spec

  • El modelo adivina y alucina archivos.
  • Cada corrida da algo distinto.
  • Nadie sabe por qué se hizo así.

✓ Con spec

  • Contexto explícito → menos alucinación.
  • Proceso repetible y revisable.
  • La decisión queda documentada.
estructura de un cambio (estilo OpenSpec)
openspec/changes/agregar-login-magic-link/
├── proposal.md   # por qué + qué (el contrato que le das a la IA)
├── tasks.md      # checklist de implementación
└── spec/         # deltas: ADDED / MODIFIED / REMOVED

Versión ligera para el hackathon

Aunque no instales OpenSpec, aplica la idea: antes de pedir que implemente algo, escríbele 5 líneas — objetivo, archivos a tocar, qué NO tocar, criterios de aceptación. Pégalas como contexto. La calidad sube muchísimo, con cualquier asistente (Claude, Gemini, Cursor…).

7 · Decisiones de arquitectura

Las preguntas que de verdad mueven la aguja

¿IA o algoritmo?

La regla: usa IA solo cuando la tarea requiere entender lenguaje, ambigüedad o contexto que no puedes expresar en reglas. Si puedes escribir la regla, escríbela — es exacta, gratis e instantánea. (El motor de matching de TeamUp es algoritmo; orwel-mind es Bayes; la IA entra solo a leer CVs y resumir.)

¿Build o buy?

PregúntateInclínate por…
¿Es tu diferenciador (el corazón de tu producto)?Build — no terceries tu ventaja.
¿Es infra resuelta (auth, pagos, analítica, email)?Buy — Supabase, Stripe, Orwel, Resend. No reinventes.
¿Lo necesitas para el lunes?Buy ahora, evalúa build después.

Lección de TeamUp

Intentamos resolver el scoring de muchos candidatos con una sola llamada gigante a la IA. Reventaba el contexto y dejaba de responder. La solución no fue un modelo más grande, fue mejor arquitectura: extraer + map-reduce + caché. Casi siempre el cuello de botella es el diseño, no el modelo.

¿Cuándo optimizar?

No antes de tiempo. En un hackathon, que funcione de punta a punta vence a que escale a un millón de usuarios. Pero conoce dónde están los límites (esta página) y dilo en tu presentación: demuestra criterio de ingeniería, y eso es justo lo que evalúa un jurado técnico.
