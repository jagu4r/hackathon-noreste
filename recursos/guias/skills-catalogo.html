El arsenal de skills de Hyperdigital

Cada skill es un poder que le instalas a tu asistente de IA. Aquí está qué son, cómo funcionan, y el detalle de cada una: por qué la creamos, qué problema resuelve y cuándo se activa.

El concepto

¿Qué es una skill, exactamente?

En palabras simples

Imagina que contratas un ayudante muy inteligente pero nuevo. Una skill es el manual que le das para una tarea específica: "así instalamos Orwel", "así escribimos documentación". Una vez que tiene el manual, lo hace bien y a nuestra manera, sin que se lo expliques cada vez.

Técnicamente: una skill es una carpeta con un archivo SKILL.md. Arriba lleva un frontmatter con un name y una description; abajo, las instrucciones. El asistente (Claude Code, Gemini, Cursor…) lee la description de todas tus skills y activa sola la que corresponde a tu tarea.

skills/mi-skill/SKILL.md
---
name: mi-skill
description: Qué hace y CUÁNDO usarla. Esta línea decide
  si el asistente la activa — escríbela con palabras clave.
---

# Título
Las instrucciones, paso a paso, en lenguaje claro.
Reglas, ejemplos de código, checklists.
  • La description es lo más importante: es lo que el asistente usa para decidir cuándo activarla.
  • No la "ejecutas" tú; se dispara cuando tu petición coincide con su propósito.
  • Una skill es portable: la copias entre proyectos y funciona igual.

orwel

Producción

Instala e integra el SDK de analítica Orwel en cualquier framework.

Por qué existe
Instalar Orwel a mano se repite en cada proyecto y es fácil equivocarse: poner la llave en el lugar incorrecto, inicializar en el servidor, o filtrar el secreto a GitHub.
Qué resuelve
Hace la instalación perfecta y segura: llave en .env, wrapper por framework (Next, React, Vue, Nuxt, Astro, SvelteKit), init en el momento correcto, y evita los errores clásicos (como el conversion async en formularios).
Cuándo se activa
Al mencionar "Orwel SDK", "orwel.track", "PUBLIC_ORWEL_KEY" o pegar una llave orwel_....

hyper-llm

Producción

Patrones de IA en producción: RAG, agentes y manejo de contexto grande.

Por qué existe
Nació de un dolor real: en TeamUp, las peticiones grandes a LLMs reventaban el contexto y el modelo dejaba de responder. Queríamos que ese conocimiento no se perdiera.
Qué resuelve
Da las recetas para que la IA aguante producción: presupuesto de tokens, extracción, map-reduce, lotes con reintentos, caché, RAG y agentes con límites. Evita el error #1 de proyectos con IA.
Cuándo se activa
"RAG", "agente de IA", "el LLM no responde", "excede el contexto", "procesar muchos con IA".

hyper-core

Producción

Arquitectura para levantar un backend nuevo multi-tenant.

Por qué existe
Cada backend nuevo empezaba de una hoja en blanco, repitiendo (y a veces olvidando) las mismas decisiones de base: aislamiento de datos, auth, estructura.
Qué resuelve
Codifica el estándar: multi-tenant con workspace_id + RLS desde el día 1, auth con Magic Link, service layer obligatorio, validación y operación mínima.
Cuándo se activa
"nuevo backend", "API desde cero", "multi-tenant", "RLS", "service layer".

hyper-sdk

Producción

Arquitectura para crear un SDK cliente nuevo con buena DX.

Por qué existe
Construir Orwel nos enseñó qué hace que un SDK sea agradable de usar (y qué lo arruina). Esa experiencia estaba en la cabeza de pocas personas.
Qué resuelve
Guía a diseñar la superficie pública primero, singleton con init, validación con mensajes claros, resiliencia invisible (cola, reintentos), empaquetado y docs.
Cuándo se activa
"crear SDK", "librería cliente", "envolver mi API", "publicar paquete".

hyper-doc

Producción

Genera documentación completa del proyecto donde se ejecuta.

Por qué existe
Los proyectos sin documentación (o con READMEs desactualizados) frenan a todo el que llega nuevo. Documentar a mano es tedioso y se pospone.
Qué resuelve
Lee el código real y genera README, arquitectura y guía de setup precisos — no inventados. Marca lo que falta y verifica que los comandos existan.
Cuándo se activa
"documenta este proyecto", "crea un README", "guía de setup", "explica la arquitectura".

hyper-papers

Producción

Escribe un "paper" técnico / case study de un proyecto implementado.

Por qué existe
El conocimiento valioso —por qué se tomó una decisión, qué se rompió y cómo se arregló— se queda en la cabeza de la gente y se pierde.
Qué resuelve
Convierte un proyecto en un documento narrativo que enseña: contexto, arquitectura, decisiones, lecciones de producción y patrones replicables. Como este Playbook.
Cuándo se activa
"haz un paper de", "case study", "documento técnico del proyecto", "post-mortem".

hyper-env

Producción

Entornos de prueba para testear features de IA de forma confiable.

Por qué existe
Probar IA es distinto: las salidas no son deterministas, cuestan dinero y son lentas. Sin un método, o no pruebas, o gastas una fortuna en cada corrida.
Qué resuelve
Da tres niveles —unit con el modelo mockeado, evals con dataset dorado, y smoke real— más cómo hacer testeable lo no determinista (assert por propiedades, caché por hash).
Cuándo se activa
"testear IA", "evaluar el modelo", "mockear el LLM", "dataset de prueba", "evals".

svelte-loading

Producción

Carga de datos en SvelteKit 2 + Svelte 5: streaming, skeletons y gotchas.

Por qué existe
Se extrajo del código real de Orwel tras pelear con pantallas que parpadean, cargas que bloquean, y un crash fatal de Svelte 5 (each_key_duplicate).
Qué resuelve
El playbook para cargar datos sin parpadeo: streamear promesas, skeletons, depends/invalidate, preload, y evitar los anti-patrones que causaron bugs reales.
Cuándo se activa
Al trabajar con load, {#await}, skeletons o el crash each_key_duplicate en SvelteKit.

Bonus

Crea tu propia skill en tres minutos

Durante el hackathon, si te encuentras explicándole lo mismo a la IA una y otra vez, conviértelo en una skill.

  • 1. Crea la carpeta skills/mi-skill/ (dentro de la convención de tu asistente, p. ej. .claude/skills/).
  • 2. Dentro, un SKILL.md con el frontmatter (name + description) y tus instrucciones.
  • 3. Escribe la description con las palabras que dispararían la skill. Listo: el asistente ya la usará.

Para el hackathon

Una buena skill captura una regla o un error que ya cometiste: "siempre que hagas X, recuerda Y". Si tu equipo crea una skill propia durante el evento y la enseña en la demo, eso demuestra dominio real de las herramientas.
